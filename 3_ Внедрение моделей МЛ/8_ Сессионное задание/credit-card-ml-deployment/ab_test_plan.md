# План A/B-тестирования сервиса прогнозирования дефолта по кредитным картам

## Цель тестирования

Цель A/B-теста — определить, приводит ли новая версия модели машинного обучения к улучшению качества прогнозирования дефолта клиентов по сравнению с текущей версией модели.

Тестирование проводится в production-like среде с использованием двух версий модели.

---

# Участники тестирования

## Контрольная группа (A)

Использует текущую модель:

```text
v1 — GradientBoostingClassifier
```

Данная модель считается базовой версией сервиса.

---

## Тестовая группа (B)

Использует новую модель:

```text
v2 — RandomForestClassifier
```

Цель тестирования — проверить, превосходит ли новая модель текущую версию по ключевым метрикам.

---

# Схема распределения трафика

Для проведения эксперимента используется случайное распределение запросов между двумя версиями модели.

Распределение:

```text
50% запросов → модель v1
50% запросов → модель v2
```

Случайное распределение обеспечивает сопоставимость групп и снижает риск систематической ошибки.

---

# Продолжительность тестирования

Планируемая продолжительность эксперимента:

```text
14 календарных дней
```

Либо до достижения минимального объёма выборки:

```text
10 000 запросов на каждую группу
```

Используется правило:

```text
Тест завершается по достижении любого из двух условий:
- прошло 14 дней;
- собрано не менее 10 000 наблюдений в каждой группе.
```

# Гипотезы

## Основная гипотеза

Проверяется улучшение качества прогнозирования дефолта.

### Нулевая гипотеза H0

```text
Между моделями отсутствуют статистически значимые различия.
```

---

### Альтернативная гипотеза H1

```text
Модель v2 демонстрирует статистически значимое улучшение по сравнению с моделью v1.
```

---

# Метрики оценки

## Основная метрика

### F1-score

Причина выбора:

В задаче прогнозирования дефолта важны одновременно:

* Precision;
* Recall.

F1-score учитывает оба показателя и позволяет сбалансированно оценивать качество модели.

Формула:

```text
F1 = 2 × Precision × Recall / (Precision + Recall)
```

---

## Дополнительная метрика

### Precision

Причина выбора:

Ложноположительные прогнозы приводят к отказу надёжным клиентам.

Высокое значение Precision означает, что большинство клиентов, отмеченных как дефолтные, действительно являются высокорисковыми.

Формула:

```text
Precision = TP / (TP + FP)
```

---

# Бизнес-метрики

Помимо технических метрик оцениваются бизнес-показатели.

---

## Снижение ожидаемых финансовых потерь

Метрика показывает объём потенциальных потерь от пропущенных дефолтов.

Формула:

```text
Expected Loss = FN × Average Default Loss
```

где:

* FN — количество пропущенных дефолтов;
* Average Default Loss — средний размер потерь по одному дефолту.

Чем меньше значение метрики, тем лучше результат.

---

## Approval Rate

Метрика показывает долю клиентов, получивших одобрение.

Формула:

```text
Approval Rate = Approved Applications / Total Applications
```

Рост данной метрики при сохранении уровня риска является положительным бизнес-эффектом.

---

# Статистический анализ

Для сравнения результатов моделей используется z-test для двух независимых выборок.

Причины выбора:

* большой объём наблюдений;
* бинарный характер исходов;
* сравнение долей успешных прогнозов.

---

# Уровень значимости

Используется стандартный уровень значимости:

```text
α = 0.05
```

Вероятность ошибки первого рода составляет 5%.

---

# Доверительные интервалы

Для каждой метрики рассчитывается:

```text
95% доверительный интервал
```

Интервалы позволяют оценить диапазон возможных значений показателей модели.

Если доверительные интервалы моделей не пересекаются, это является дополнительным подтверждением различий между ними.

---

# Критерий успешности теста

Новая версия модели считается успешной, если одновременно выполняются следующие условия:

1. F1-score модели v2 выше F1-score модели v1.
2. Precision модели v2 не ниже Precision модели v1.
3. Результат статистически значим:

```text
p-value < 0.05
```

4. Отсутствует ухудшение бизнес-метрик.

---

# Возможные риски

Основные риски эксперимента:

* недостаточный объём данных;
* сезонные изменения поведения клиентов;
* изменение структуры входящего трафика;
* ошибки разметки данных.

Для снижения рисков используется случайное распределение запросов.

---

# Rollback Plan

Если в ходе тестирования наблюдается:

* снижение F1-score;
* снижение Precision;
* рост финансовых потерь;
* технические ошибки сервиса;

тестирование немедленно прекращается.

Весь трафик переводится обратно на модель:

```text
v1 — GradientBoostingClassifier
```

---

# Итоговое решение

После завершения тестирования формируется отчёт, содержащий:

* результаты метрик;
* статистические выводы;
* доверительные интервалы;
* анализ бизнес-эффекта.

На основании отчёта принимается одно из решений:

1. Полный переход на модель v2.
2. Дополнительное тестирование модели v2.
3. Сохранение текущей версии v1.

---

# Связь с архитектурой сервиса

В текущей реализации переключение между моделями осуществляется через параметр:

```json
{
  "model_version": "v1"
}
```

или

```json
{
  "model_version": "v2"
}
```

Такой подход позволяет проводить A/B-тестирование без изменения API и без остановки сервиса.
