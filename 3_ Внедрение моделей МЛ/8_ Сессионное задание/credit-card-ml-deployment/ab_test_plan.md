# План A/B-тестирования

## 1. Цель

Сравнить две версии модели прогнозирования дефолта по кредитным картам:

- v1 — контрольная группа (текущая модель, GradientBoostingClassifier)
- v2 — тестовая группа (новая модель, RandomForestClassifier)

## 2. Разделение трафика

- Случайное распределение 50/50.
- 50% запросов направляются на v1.
- 50% запросов направляются на v2.

Распределение может выполняться:
- на уровне API gateway (API gateway — шлюз API),
- либо на уровне приложения по user_id / hash (hash — хеш).

## 3. Продолжительность теста

- Минимум 2–4 недели.
- Или до достижения заранее рассчитанного минимального размера выборки.

## 4. Основная метрика

- F1-score для класса дефолта (1)

### Почему:
F1-score балансирует:
- Precision (precision — точность положительных предсказаний)
- Recall (recall — полнота обнаружения дефолтов)

Это важно, потому что:
- ложноположительные решения снижают выдачу кредитов;
- ложноотрицательные решения увеличивают финансовые потери.

## 5. Дополнительная метрика

- Precision для класса дефолта

### Обоснование:
Для банка важно не переоценивать риск и не отклонять слишком много хороших клиентов.

## 6. Бизнес-метрики

### 6.1. Снижение ожидаемых финансовых потерь
Формула:
Expected Loss = FN * Avg_Default_Loss

Где:
- FN — количество ложноотрицательных прогнозов
- Avg_Default_Loss — средний убыток по одному дефолту

### 6.2. Доля одобренных заявок при фиксированном уровне риска
Формула:
Approval Rate = Approved_Applications / Total_Applications

Сравнение выполняется при одинаковом пороге риска или одинаковом допустимом уровне дефолта.

## 7. Статистический анализ

### Для долей / бинарных исходов:
- z-test (z-test — z-тест для сравнения долей)

### Для сравнения средних бизнес-показателей:
- t-test (t-test — t-тест)

## 8. Доверительные интервалы

- Строятся 95% confidence interval (confidence interval — доверительный интервал) для:
  - разницы F1-score (через bootstrap, bootstrap — бутстрэп);
  - разницы Precision;
  - разницы ожидаемых потерь.

## 9. Критерий успешности теста

Тест считается успешным, если одновременно выполняются условия:

1. F1-score у v2 статистически значимо выше, чем у v1;
2. Precision у v2 не хуже v1 (или выше);
3. Ожидаемые финансовые потери не увеличиваются;
4. 95% доверительный интервал для ключевой бизнес-метрики не пересекает 0 в сторону ухудшения.

## 10. Связь с архитектурой

Поддержка A/B-теста в сервисе обеспечивается полем:
- `model_version`

Это позволяет:
- явно тестировать обе версии через API;
- логировать результаты отдельно;
- упростить rollback (rollback — откат) на v1 при неудачном тесте.
