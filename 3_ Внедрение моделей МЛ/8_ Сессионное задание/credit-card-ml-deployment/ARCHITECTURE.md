# Архитектура сервиса прогнозирования дефолта по кредитным картам

## Общая архитектура решения

В рамках проекта реализован REST API сервис для прогнозирования вероятности дефолта клиента по кредитной карте.

Сервис предоставляет два эндпоинта:

* GET /health — проверка работоспособности сервиса;
* POST /predict — получение предсказания модели.

Обученные модели загружаются из файлов формата Joblib и используются для выполнения инференса.

Общая схема решения:

```text
Client
   │
   ▼
Flask API
   │
   ▼
Model Handler
   │
   ├── model_v1.pkl
   └── model_v2.pkl
   │
   ▼
Prediction
   │
   ▼
JSON Response
```

# Монолитная архитектура vs микросервисы

## Монолитная архитектура

В монолитной архитектуре все компоненты системы находятся внутри одного приложения:

* API;
* бизнес-логика;
* загрузка моделей;
* логирование;
* обработка запросов.

Преимущества:

* простая разработка;
* простое тестирование;
* минимальные накладные расходы;
* удобный деплой;
* подходит для небольших проектов.

Недостатки:

* ограниченная масштабируемость;
* сложнее независимо обновлять отдельные компоненты.

---

## Микросервисная архитектура

В микросервисном подходе система разделяется на независимые сервисы:

* сервис инференса;
* сервис логирования;
* сервис мониторинга;
* сервис A/B-тестирования;
* сервис обработки батч-запросов.

Преимущества:

* независимое масштабирование;
* отказоустойчивость;
* удобство поддержки крупных систем.

Недостатки:

* более сложный деплой;
* сложность мониторинга;
* дополнительные сетевые издержки.

---

## Обоснование выбора архитектуры

Для данного учебного проекта выбрана монолитная архитектура.

Причины выбора:

| Критерий                      | Монолит       | Микросервисы |
| ----------------------------- | ------------- | ------------ |
| Простота реализации           | Высокая       | Низкая       |
| Скорость разработки           | Высокая       | Низкая       |
| Требования проекта            | Соответствует | Избыточно    |
| Сложность сопровождения       | Низкая        | Высокая      |
| Подходит для учебного проекта | Да            | Нет          |

Вывод:

Для сервиса прогнозирования дефолта с небольшим количеством пользователей монолитная архитектура является наиболее рациональным решением.

# Концепция использования RabbitMQ

RabbitMQ является брокером сообщений и позволяет организовывать асинхронное взаимодействие между сервисами.

В рамках масштабирования данного решения RabbitMQ может использоваться для:

* асинхронной обработки батч-предсказаний;
* отправки логов;
* формирования отчётов;
* интеграции с внешними банковскими системами;
* уведомлений пользователей.

Пример сценария:

```text
Client
   │
   ▼
RabbitMQ Queue
   │
   ▼
Prediction Worker
   │
   ▼
Database
```

Преимущество подхода заключается в разгрузке API и повышении производительности системы.

---

# Логирование

В проекте реализовано логирование запросов и ответов API.

Логи сохраняются в:

```text
logs/api.log
```

Формат логирования:

```json
{
  "timestamp": "2026-06-15T12:00:00",
  "endpoint": "/predict",
  "model_version": "v1",
  "prediction": 1,
  "probability": 0.75
}
```

Логируются:

* время запроса;
* используемая модель;
* результат предсказания;
* вероятность дефолта;
* ошибки выполнения.

---

# Мониторинг и ELK Stack

В production-среде логи могут собираться через ELK Stack.

ELK включает:

* Elasticsearch — хранение логов;
* Logstash — обработка логов;
* Kibana — визуализация.

Преимущества:

* централизованный сбор логов;
* мониторинг ошибок;
* анализ производительности;
* построение дашбордов.

---

# ONNX

ONNX (Open Neural Network Exchange) представляет собой формат хранения моделей машинного обучения.

Преимущества использования ONNX:

* ускорение инференса;
* переносимость между платформами;
* снижение потребления ресурсов;
* возможность использования ONNX Runtime.

В данном проекте модель может быть конвертирована из Scikit-Learn в ONNX для повышения производительности при эксплуатации.

---

# uWSGI и NGINX

Текущий сервис запускается через встроенный Flask-сервер.

Для production-развёртывания рекомендуется следующая схема:

```text
Internet
   │
   ▼
NGINX
   │
   ▼
uWSGI
   │
   ▼
Flask Application
```

NGINX выполняет:

* балансировку нагрузки;
* SSL-терминацию;
* маршрутизацию запросов.

uWSGI выполняет:

* запуск нескольких процессов приложения;
* управление воркерами;
* повышение производительности.

# DVC

DVC (Data Version Control) используется для контроля версий данных и моделей.

Основные возможности:

* хранение больших файлов;
* версионирование датасетов;
* воспроизводимость экспериментов;
* контроль изменений моделей.

Для данного проекта DVC мог бы использоваться для хранения различных версий датасета кредитных клиентов.

# MLflow

MLflow используется для отслеживания экспериментов машинного обучения.

Основные возможности:

* логирование параметров моделей;
* сохранение метрик;
* сравнение экспериментов;
* хранение артефактов.

В данном проекте MLflow мог бы использоваться для сравнения моделей:

* GradientBoostingClassifier;
* RandomForestClassifier.

# Бизнес-метрики

Помимо технических метрик необходимо оценивать бизнес-эффект модели.

## Expected Loss Reduction

Метрика показывает снижение ожидаемых финансовых потерь.

Формула:

```text
Expected Loss = FN × Average Default Loss
```

где:

* FN — количество пропущенных дефолтов;
* Average Default Loss — средний убыток по одному дефолту.

Чем меньше значение метрики, тем лучше модель.

---

## Approval Rate

Метрика показывает долю одобренных заявок.

Формула:

```text
Approval Rate = Approved Applications / Total Applications
```

Повышение данного показателя при сохранении уровня риска является положительным бизнес-эффектом.

# Масштабирование системы

При увеличении нагрузки возможны следующие улучшения:

1. Переход к микросервисной архитектуре.
2. Использование RabbitMQ.
3. Использование Kubernetes.
4. Внедрение ELK Stack.
5. Использование ONNX Runtime.
6. Разделение сервисов инференса и мониторинга.

Данные изменения позволят обслуживать значительно больший объём запросов без изменения бизнес-логики системы.
