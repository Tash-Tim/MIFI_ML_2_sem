# Архитектура сервиса

## 1. Выбранный подход: монолит (monolith — монолитная архитектура)

Для данного учебного проекта выбран монолитный подход.

### Обоснование:
- Проект небольшой по масштабу.
- Требуется минимально достаточный production-like (production-like — приближенный к промышленному) pipeline.
- Один Flask-сервис полностью покрывает задачу:
  - загрузка модели;
  - API для инференса (inference — предсказание);
  - health-check (health-check — проверка работоспособности);
  - логирование;
  - поддержка двух версий модели для A/B-теста.

### Почему не микросервисы (microservices — микросервисная архитектура):
- Избыточная сложность для учебного кейса.
- Увеличение операционных затрат.
- Появляется необходимость отдельного API gateway (API gateway — шлюз API), service discovery (service discovery — обнаружение сервисов), оркестрации и межсервисного мониторинга.

## 2. RabbitMQ (RabbitMQ — брокер сообщений)

В текущем проекте RabbitMQ не реализуется, но может использоваться при масштабировании.

### Потенциальные сценарии:
- асинхронная обработка batch predictions (batch predictions — пакетные предсказания);
- очередь на повторную обработку неуспешных запросов;
- асинхронное логирование;
- отправка событий в аналитический контур;
- накопление данных для offline re-training (offline re-training — переобучение вне онлайн-сервиса).

## 3. Логирование и мониторинг

### Что логируется:
- endpoint;
- версия модели;
- входные признаки;
- ответ API;
- ошибки.

### Формат:
JSON (JSON — структурированный формат обмена данными).

### Куда:
- `logs/api.log`

### Как в production:
- сбор через ELK stack (ELK stack — Elasticsearch + Logstash + Kibana);
- возможна интеграция с Grafana + Loki.

## 4. DVC и MLflow

### DVC (Data Version Control — контроль версий данных)
Используется для:
- версионирования датасетов;
- фиксации используемых версий входных данных;
- воспроизводимости экспериментов.

### MLflow (MLflow — трекинг экспериментов)
Используется для:
- логирования метрик моделей;
- хранения параметров обучения;
- регистрации версий моделей;
- упрощения перехода от эксперимента к production.

## 5. ONNX-ML (ONNX-ML — формат переносимых моделей)

Модель можно конвертировать в ONNX-формат для:
- ускорения инференса;
- унификации развертывания;
- запуска вне Python-среды.

Типовой стек:
- `skl2onnx`
- `onnxruntime`

## 6. uWSGI + NGINX

В production-среде:
- uWSGI (uWSGI — WSGI-сервер) запускает Python/Flask-приложение;
- NGINX (NGINX — reverse proxy, обратный прокси) принимает внешние HTTP-запросы.

### Зачем:
- балансировка нагрузки;
- обработка таймаутов;
- SSL termination (SSL termination — завершение TLS/SSL на прокси);
- более стабильная работа под нагрузкой.
